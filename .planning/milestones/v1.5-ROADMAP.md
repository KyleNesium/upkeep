# v1.5 — Single-Shot Update Skill (macOS)

**Status:** planning
**Branch:** `feat/v1.5-single-shot`
**Started:** 2026-05-28
**Predecessor:** v1.4 (Fast Discovery + Synthesis, shipped 2026-05-18)

## Problem

v1.4 cut discovery+plan from ~120s to ~16s by replacing four scout agents and the synthesizer agent with bash. But user-perceived end-to-end time is still bad because:

1. **Multi-turn skill overhead.** `SKILL.md` is structured as 5+ steps (1m → 2m → 2.5m → 3m → 4m → 5m). Each step is an LLM round-trip, even when the work inside is a single bash command. ~3–5s × 5 turns = 15–25s of pure orchestration latency on top of any actual work.
2. **Enrichment in the critical path.** Step 2.5m's `changelog-reader` + `project-impact` agents fire *before* the approval gate. WebFetch is slow; manifest walks across `~/workspace` are slow. Adds 30–60s of pre-gate wait the user can't dismiss.
3. **`brew update` runs every invocation.** 8–14s of the discover.sh wall time is `brew update` refreshing formula metadata. Re-runs even if the metadata is 2 minutes old.
4. **`failure-diagnoser` is an LLM call per failing tool.** Most failures match ~6 well-known patterns (Ruby ≤ 2.6, native build deps, EACCES, dyld load, arch mismatch, pipx venv). Pattern table is faster and more deterministic.

User feedback (2026-05-28): "this skill takes way too long to run, we need to make it more efficient, people complain about it and won't use it in its current state."

## Goal

`/upkeep:update audit` returns in **<3s** on a warm cache.
`/upkeep:update packages` reaches the approval gate in **<5s** on a warm cache.
Apply phase runs at package-manager-native speed (cannot be compressed).

Total LLM turns from user invocation to approval gate: **2** (was: 5–6).

## Architecture change

**v1.4 (current):** SKILL.md is the orchestrator. Each step is a Claude turn that runs bash + interprets results + decides next step. Scripts (`discover.sh`, `synthesize.sh`) handle individual phases.

**v1.5 (proposed):** A single fat script `scripts/update.sh` is the orchestrator. SKILL.md becomes ~50 lines of "parse user intent, invoke `update.sh <mode>`, render the gate from its JSON output, on approval invoke `update.sh apply <plan-id>`, render the report."

The LLM is responsible for exactly three things:
1. Parsing user intent → which sub-mode (audit/skills/packages/all + flags)
2. Rendering the approval gate from structured JSON
3. Rendering the final report from structured JSON

Everything else is bash. No multi-step turn dance.

## Phases

### Phase 1 — `scripts/update.sh` (single-shot orchestrator)

One script, two commands:
- `update.sh plan <mode> [--advisor] [--no-cache]` → emits `{discovery, plan, gate_render}` JSON to stdout
- `update.sh apply <plan-file>` → reads plan JSON from file, runs dispatcher + post-flight + pattern-table diagnoser + writes history + emits `{report_render}` JSON to stdout

Internally, `plan` composes the existing `discover.sh` + `synthesize.sh` outputs and adds the gate render. No new logic, just composition.

`apply` extracts the v1.4 SKILL.md Step 3m + 4m + 4.5m + 5m bash into one place. Plan is read from a temp file (mktemp at end of `plan` command, path returned in JSON) so SKILL.md doesn't have to round-trip the plan JSON through prompt context.

### Phase 2 — brew-update TTL cache

In `discover.sh`:

```bash
BREW_SENTINEL="$HOME/Library/Caches/Homebrew/api/formula.jws.json"
BREW_TTL="${UPKEEP_BREW_TTL:-3600}"  # 1 hour default
if [ "${UPKEEP_NO_CACHE:-0}" = "1" ] || \
   [ -z "$(find "$BREW_SENTINEL" -mmin -$((BREW_TTL/60)) 2>/dev/null)" ]; then
  brew update >/dev/null 2>&1
fi
```

`--no-cache` flag forces refresh. Default TTL 1h. Sentinel is brew's own JSON file (already maintained by `brew update`).

**Expected impact:** warm-run discovery drops from 16s → ~2s.

### Phase 3 — Enrichment behind the gate, not in front of it

Two options, picked by the user via flag:

- **Default:** No enrichment runs before the gate. Plan shows raw version bumps + compat-matrix warnings only. Gate appears fast.
- **`--advisor`:** v1.4's `changelog-reader` + `project-impact` agents fire *after* the gate, in parallel with `brew upgrade` (which is the long pole anyway). Results merged into the final report instead of the gate.

This preserves the advisor value for users who want it, removes it from the latency critical path for everyone.

### Phase 4 — Pattern-table failure diagnoser (replaces LLM agent)

`scripts/diagnose.sh`: reads `(tool, rc, log_path)` triples, emits diagnoses JSON with the same schema as v1.4's `failure-diagnoser` agent. Internally a case statement over known regexes:

| Pattern | Root cause | Suggested fix (text only, never executed) |
|---|---|---|
| `requires Ruby version >= [0-9]` | system Ruby too old | `brew install mise && mise use -g ruby@3.3` |
| `Permission denied @ rb_sysopen` / `EACCES` | permissions | `gem install --user-install <name>` |
| `checking for .* no` (extconf) | missing build dep | `brew install <suggested-lib>` |
| `ImportError: No module named` | broken pipx venv | `pipx reinstall <name>` |
| `dyld\[.*\]: Library not loaded` | broken native module | `<pkg-manager> reinstall <name>` |
| `incompatible cpu-arch` / `wrong ELF class` | arch mismatch | `arch -arm64 <pkg-manager> install <name>` |
| `no compatible version found` | version solver constraint | `<pkg-manager> info <name>` (manual inspection) |

Fallback when no pattern matches: emit one "Investigate manually" diagnosis with a pointer to the log path.

Severity rubric same as v1.4. Output JSON identical to v1.4 (so SKILL.md gate rendering doesn't change).

### Phase 5 — Eager discovery hook (optional, post-MVP)

A `SessionStart` Claude Code hook that runs `discover.sh` in the background and writes `/tmp/upkeep-discovery-cache.json` with a timestamp. The `plan` command reads the cache if the file exists and is <60s old.

Gated by env var `UPKEEP_EAGER=1` (off by default — adds session-start IO that not every user wants).

Defer if Phase 1–4 hits the targets without it.

### Phase 6 — Refresh planning docs

`.planning/ROADMAP.md` and `STATE.md` stop at v1.1 even though v1.2, v1.2.1, v1.2.2, v1.3, v1.3.1, v1.4 all shipped. Bring them current through v1.5.

## Acceptance criteria

- `time /upkeep:update audit` (warm cache, jq installed): **< 3s** end-to-end
- `time /upkeep:update packages` to approval gate (warm cache): **< 5s** end-to-end
- Cold cache (`--no-cache` or no brew metadata): same as v1.4 (~16s)
- All v1.4 security invariants preserved: no `command`/`preconditions` fields, hardcoded dispatcher allowlist, discovery sanitization, trust-on-first-use for skill repos
- Pattern-table diagnoser produces same shape JSON as v1.4 agent for the 7 patterns above
- No regression on the v1.3 codex-review findings (5 critical bugs) or v1.4 fast-path validation (16s discovery, valid JSON, security PASS) — both must still hold

## Out of scope (v1.5)

- Linux/WSL2 fast-path port — separate v1.6 milestone
- Auto-update mechanism for stale installed plugin (Claude Code's responsibility, not upkeep's)
- New package managers (already covers brew/npm/pipx/gems/uv/bun/mas/macos)

## Risk

- **`update.sh` becomes a 1000+ line god script.** Mitigation: keep `discover.sh`, `synthesize.sh`, `diagnose.sh` as separate units; `update.sh` is just composition + dispatcher + post-flight + history.
- **Cached `brew update` shows stale plan.** Mitigation: 1h TTL is short enough that real users get fresh enough metadata; `--no-cache` flag for the paranoid; CHANGELOG note explaining the trade-off.
- **Pattern-table misses a new failure mode.** Mitigation: fallback "Investigate manually" path; new patterns can be added in v1.5.x without touching the agent layer.
